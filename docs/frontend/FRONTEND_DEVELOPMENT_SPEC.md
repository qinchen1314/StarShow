# StarShow 买家端前端开发规格

**状态：评审稿 · 2026-11-22 · Phase 6 设计输入**

面向实现、评审和验收买家端的开发者。首版以移动网页为主，在桌面浏览器完成同一条购票链路。交付目标是让用户从演出详情找到下一步，自己选到可尝试购买的座位，在提交结果不明确时找回原请求，并从原单继续支付、查看电子票或追踪退款。

本文的路由、配色、尺寸、控件和性能预算是待评审的前端方案。按 Phase 6 的发布目标，买家页面放在 `web-console/`，浏览器直接加载 HTML、CSS 和 JavaScript，无需打包。接口尚未就绪的页面用合成数据评审。实际可用的后端能力以契约和验收回执为准。 [API 契约](../contracts/API_CONTRACT.md) · [项目进度](../PROGRESS.md)

### 2.2 路由与返回规则

零构建首版建议采用 `web-console/#/…` 的 hash 路由，部署在子路径时刷新仍落在同一个静态入口。表中的路径是前端视图地址。

| 路径 | 页面任务 | 刷新或返回 |
| --- | --- | --- |
| `/shows?city=…` | 找到能去的演出 | 保留城市。站内返回恢复列表位置与已经加载的项目。直接打开从第一页读取。 |
| `/shows/:showId` | 看场次、规则与入口状态 | 重新查详情。已登录时加载本人预约或交易入口提示。 |
| `/shows/:showId/waiting-room` | 看候场与准入进度 | 后续路由。刷新或换设备先查本人候场记录，再决定可用操作。 |
| `/shows/:showId/seats` | 选票档、分区和座位 | 返回同场次时，重查票价、库存和分区布局，再恢复仍然有效的选择。 |
| `/shows/:showId/checkout` | 核对订单并提交 | 同一登录会话内返回保留仍有效的草稿。缺草稿时回选票，有在途请求时优先续查。 |
| `/orders/confirm?showId=…` | 等待受理后的原单结果 | 有本机请求号就续查该请求，换设备按场次查本人当前订单。找到已落库的订单后可进入详情。 |
| `/orders`、`/orders/:orderNo` | 找回订单、支付与售后 | 订单列表仅渲染服务端返回的记录。可以单列「确认中」入口，由已登录账号的本机续查记录提供恢复线索。 |
| `/orders/:orderNo/payment`、`/orders/:orderNo/tickets`、`/orders/:orderNo/refund` | 回到原单处理一个动作 | 先查本人原单与对应状态。支付回跳结果由原支付单查询确认。 |
| `/account/login`、`/account/identity`、`/account/reservations`、`/account/notifications` | 登录、实名、查看预约和通知 | 登录或实名完成后回同站原任务。返回目标从受控内部路由解析，跳转前重新查询当前状态。 |

发现页使用「演出」「订单」「我的」三个一级入口。详情返回列表，选座返回详情，核对返回选座或票档。提交后用确认页替换当前核对页的浏览历史项。确认页提供「查看我的订单」，浏览器后退到前序视图时检查是否存在原单。支付页返回原订单详情。切换城市重置游标。订单地址用订单号定位，服务端检查账号的订单归属。访问令牌、证件、支付参数与验票码留在各自流程内。

## 3. 视觉、版式与去模板化

### 3.1 视觉方向

用主办方海报或获授权的演出影像提供情绪和颜色。浏览页采用暖白背景、近黑正文和单一深青绿操作色。进入选座和结账后，画面由舞台方位、座位编码、价格和订单状态主导。深色氛围只来自海报本身，页面导航、正文与交易控件采用稳定的浅色底。

设计做品牌初审时只需比较演出详情、选座、待支付三屏。移除海报后，每屏应仍能从标题、流程位置与主操作区分用途。进入售卖状态后，用户要能直接指出场次、价格、限制和下一步。

### 3.2 颜色和尺寸

以下值供首轮视觉稿与 CSS 自定义属性使用。对比度是对指定前景和背景的静态计算，组件实现时复测默认、选中、按下、焦点和高对比模式。

| Token | 值 | 用途 |
| --- | --- | --- |
| `--page` / `--surface` | `#F8F7F3` / `#FFFFFF` | 页面底和需要遮住滚动内容的底栏、弹层 |
| `--ink` / `--ink-muted` | `#211F1C` / `#625D54` | 正文和辅助文字，在页面底约 15.34:1 / 6.10:1 |
| `--action` / `--action-ink` | `#184C43` / `#FFFFFF` | 主操作，白字约 9.75:1。正文内链接显示下划线 |
| `--line` / `--control-line` | `#DED9D0` / `#786F62` | 行分隔与需要可辨识边界的控件。浅分隔线用于装饰 |
| 成功 / 注意 | `#225A47` on `#EAF3ED` / `#87550D` on `#FAF0DB` | 已确认、接近截止或价格变化，配明确文字 |
| 错误 / 信息 | `#8E3438` on `#FAEBEA` / `#245469` on `#EAF2F6` | 提交错误与可恢复等待，配文字和适用的操作 |

字体使用平台中文无衬线字体，优先 `PingFang SC`、`Microsoft YaHei`、`Noto Sans CJK SC` 和系统兜底。数字使用等宽数字特性以避免倒计时跳动。正文 `16px / 1.55`，辅助文字 `14px / 1.45`，场次页标题移动端 `26–30px`、桌面 `32–40px`，支付金额 `24–28px`。字体能跟随用户放大，长演出名完整换行。价格和日期按真实字段排版。

| 布局 | 具体要求 |
| --- | --- |
| 320–599 CSS px | 单列，320–359 px 横向边距 16 px，其余 20 px。演出列表用约 88×117 px 海报配文字。票档行允许价格和状态换行。 |
| 600–1023 CSS px | 页面边距 24 px。演出列表可并排两列。选座、核对和支付保持单主列，摘要在关联内容之后。 |
| 1024 CSS px 起 | 主容器最大宽 1200 px，边距至少 32 px。详情海报约 280 px，内容间距 32 px，信息列自适应。购物流程仅在地图与已选摘要需要同时可见时使用双列。 |
| 共用尺寸 | 间距用 4、8、12、16、24、32、48 px。普通图片区圆角 8 px，按钮 8 px，弹层 12 px。一般按钮最小高度 44 px。底栏高度随内容和安全区变化，正文预留等高滚动空间。 |

海报用 `3:4` 固定比例容器。主办方原图比例不同且裁切会损害人物、标志或关键信息时，改用等比留边。首屏图给出尺寸以留好位置，列表后续图延迟加载。海报缺失时用同底色和原演出标题作为回退。

### 3.3 「雷霆方块」的评审判定

这里把用户说的「雷霆方块」落实为可点名的问题。每条都应在 390 px 和 1440 px 的真实状态截图中检查。

| 拦下的表现 | 修改方法 | 评审证据 |
| --- | --- | --- |
| 同一屏并列多个等大方块，每个都带大图标、边框、阴影和标题，重要性无分级 | 规则与信息改成标题下的连续行。只为真实演出列表保留可重复单元，为选座保留分区对象。 | 场次、票价和购票按钮能在五秒内指出。设计稿中每条边框都能对应交互边界或列表分隔。 |
| 层层卡片、发光边框、玻璃蒙层、高饱和渐变、网格光斑、滚动触发的大面积位移 | 用白底、留白、分隔线和字体大小拉开层级。弹层只用一层遮罩。演出氛围由授权海报提供。 | 检查首屏和完整滚动截图。交易内容只使用约定的设计变量。 |
| 多个同等醒目的按钮、把城市和时间也做成状态胶囊、每个票档换一组主题色 | 同一任务区一个主按钮。元数据直接排成文本。票档图例颜色只用于地图，并始终贴价格和文字。 | 扫描待开售、在售、售罄、订单确认和退款五种状态，主操作位置可预测。 |
| 「解锁精彩现场」、假人气、倒计时数字翻牌、轮播占住首屏 | 文案用真实演出名、时点、状态和动作。首版发现页由城市和演出列表直接开始。等待时间只展示有服务端事实的值。 | 审核每个数量和时间的字段来源。浏览与请求恢复无持续干扰动画。 |
| 所有页面套用一个模块模板 | 发现用海报列表，详情用演出信息区和规则段落，选座由地图主导，交易页用摘要行和固定操作栏。 | 并排检查详情、选座和确认三屏，视觉中心分别落在演出、当前分区和订单状态上。 |

## 4. 逐页开发规格

| 页面 | 从顶部到底部 | 主操作与状态 |
| --- | --- | --- |
| 演出列表 | 城市入口 → 列表标题 → 演出海报、名称、场馆、演出日期 → 「查看更多」 | 默认显示已配置城市或全部场次，变更城市后重查。首屏失败在列表区显示「重新加载演出」。翻页失败在末尾重试并保留已加载项。全文搜索、分类和起价待后端契约支持后接入。 |
| 演出详情 | 返回 → 海报、标题、时间、场馆 → 开售状态、票档 → 实名、限购、退款、入场规则 → 演出介绍 → 底部入口 | 有已知原单或在途请求时优先提供续查。其余已登录用户读预约状态的 `nextAction`。符合购票条件时按座位模式显示「选座购票」或「选择票档」。允许预约、需要实名或暂时售罄时，分别提示预约开票、完成实名或查看最新余票。停售保留已有订单入口。 |
| 登录、实名与预约 | 返回 → 单列字段 → 字段错误 → 提交按钮 → 当前结果 | 登录和实名完成后回原任务。登录失败可在当页保留手机号。密码及证件信息不写入跨页草稿。预约成功展示服务端开售时间，改期后采纳最新版本与通知。 |
| 候场 | 演出名、开售时间 → 当前候场状态 → 一句资格说明和下一步 | 后续能力。仅在契约提供时显示候场位置、预计时间或资格截止。得到准入时显示「进入选座」。资格过期后按服务端引导回原队列或重新加入。风控挑战有可访问的替代入口，原排队优先级与宽限以服务端状态为准。 |
| 选票／选座 | 场次与模式 → 票档或分区 → 舞台方向、地图与图例 → 当前选座摘要 → 底栏总价与「核对订单」 | 自动配座只展示可选票档、数量和配座说明。自主选座见第 5 节。切换票档或分区保留按同场规则仍有效的选择。价格、数量和版本有效时才进入核对。 |
| 核对订单 | 演出名和场次 → 票档、座位或配座说明 → 可用的实名信息 → 退款规则摘要 → 合计与「提交订单 · ¥…」 | 座位行有编辑入口。#21 接入后可逐票指定观演人，并提供观演人编辑入口。等待提交响应时显示「正在提交…」并防止重复点击。提交结果待确认时提供原请求的续查入口。 |
| 订单确认与订单列表 | 状态标题 → 演出及已知订单号 → 提示 → 当前动作 → 订单记录 | 确认中写「请求已收到，订单确认中」，首响应丢失改用「正在查找这次购票请求」。离开时提供「查看我的订单」。没有服务端订单号时省去订单号一行。待支付、出票中、已关闭和退款状态都能回到原单。 |
| 待支付与电子票 | 订单状态 → 金额及支付截止 → 支付或查单 → 电子票入口 | 支付期限来自第 5 节的服务端字段。已付款但未出票时显示「已付款，正在出票」。账号通过订单归属校验后可查看票号、座位与入场条件。读屏能读取票面字段。验票凭证留在票页，从列表、日志和分析数据中排除。 |
| 退票与退款进度 | 原单概要 → 资格 → 金额或进度 → 下一步 | 首版在已启用 Mock 售后且确定可退的隔离演示中支持从 `PAID` 或 `TICKETED` 原单申请现有全额退款，由后端再次裁决资格。阶梯报价接入后列出原实付、手续费、实退和报价截止，跨档或过期重新确认。资金、票据与订单状态分别显示。 |

演出详情和选票页的固定底栏采用「左侧上下两行摘要，右侧主按钮」。座位页摘要显示所选张数及合计。订单确认中把下一步放入普通内容流，用户可离开并找回原单。

### 4.1 三张关键页面的排版

| 画面 | 移动端 390 px | 桌面 1440 px |
| --- | --- | --- |
| 演出详情 | 约 104×139 px 海报靠左，名称与时间靠右。长标题无法在右侧舒展时，完整标题移到海报区前后的通栏。接下来用行展示场馆、票档、实名和规则摘要，再进入正文。底栏固定当前动作。 | 约 280 px 海报与场次信息并排。右侧信息列先放日期、场馆和状态，再放购票入口与规则。正文从该信息列下方开始，页内锚点只用于确有相应内容的规则段。 |

## 5. 座位、订单与支付状态

### 5.1 座位选择

全场图用于识别舞台和分区。点分区或选同名列表项进入区域视图，并提供「回全场」与「重置缩放」。选定分区后，从分区座图接口读 `rowNo`、`colNo`、`segmentId` 和 `selectable` 来画座位。带场馆形状、分区轮廓和舞台方向的全场图使用经确认的场馆资产。资料不足时从「分区及票价」列表进入对应分区。

- 点可选座位立即更新本地已选列表和合计。列表每行写「分区、排、号、票价」，有移除按钮。页面提示「座位以提交结果为准」。当前自主选座订单限同一票档、同一分区。浏览其他分区时保留已选座位，实际改选其他分区或票档时先让用户确认替换。
- 座位索引 `seatIndex` 与场次、分区和 `layoutVersion` 一起识别。走道从 `segmentId` 区分。有连座规则时在图例旁说明座位须同排且中间无间隔或走道。无法按此规则核对时停在选座页并提示修正，后端仍做最终校验。
- 同一场次库存先比较 `saleConfigVersion`，同一场次和分区的座图先比较 `layoutVersion`。同版本采用较新的有效 `asOf`。版本或快照时间无法验证时，等待新快照后再提交。标为 `stale` 的库存带时间标签展示，恢复提交需确认当前仍在售且座位或数量可选。切换账号、场次或分区后，丢弃旧页面发出的响应。
- `A0204` 以业务数据中的 `showId, zoneId, layoutVersion` 定位，使用可选的 `conflictSeatIndices` 标出冲突座位。缺冲突列表时刷新该区并比对当前选择。只移除失效座位，键盘焦点落到冲突提示的「返回选座」按钮。 `A0205` 重查详情及当前分区，清理无法验证的选择。 `A0308` 重查当前价格并显示新旧金额，用户再次确认后依据原请求状态继续。
- 选座支持点击、触摸以及独立的分区和座位列表。列表可按排筛选，点击选择和移除与图形共享状态。图形可缩放和拖动，另设「放大」「缩小」「重置」与列表跳转入口。普通页面保留原生纵向滚动和浏览器缩放。

| 库存或售卖事实 | 提示 | 可用操作 |
| --- | --- | --- |
| `PREPARING` | 「尚未开售」及最新官方时间 | 查看详情或按本人资格预约。 |
| `OPEN` | 可尝试购票，选中后显示具体座位或票档 | 核对订单前满足数量、规则及版本要求。 |
| `SOLD_OUT` | 「此票档暂时售罄」 | 「查看最新余票」。开售窗内接到更新且确认可购才恢复提交。 |
| `STOCK_UNAVAILABLE`、`503/B0201` | 「暂时无法确认余票」 | 按 `Retry-After` 或服务端重试建议恢复对应区域。保留草稿，暂停受影响的提交，其他独立有效档位仍可浏览。 |

### 5.2 原单续查

用户首次确认时生成一个 `clientRequestId`，发请求前保存本人、场次的续查线索。首版自动恢复优先用第 5.2 节列出的查询接口。刷新后只恢复请求号或订单号，所以恢复动作使用查询。当前会话内若需要重发同一次提交，原购票参数必须完整保留。服务端确认未完成预扣且同号可续交时，才携带当前有效的抢票凭证提交。结果仍为未知时继续查单。用户改数量、座位或价格时，先等原请求明确结束且服务端允许重新发起，再生成新请求号。

| 服务端事实 | 展示与后续动作 |
| --- | --- |
| V4 返回 HTTP 202、业务码 `00202`、状态 `PENDING_CONFIRM` | 跳转确认中并带上已知原单号。受理后的可用操作是续查。 |
| `SUBMITTING`、`PENDING_CONFIRM`、`UNKNOWN`、`B0103`、网络无响应 | 知道订单号时查 `GET /api/v1/orders/{orderNo}/status?showId=…`。只知道请求号时查 `GET /api/v1/seckill/requests/{clientRequestId}?showId=…`。换设备时查 `GET /api/v1/orders/current?showId=…`。三个入口都使用本人登录态。 |
| 目标为原单且返回 `WAIT_PAY` | 按 `nextAction` 显示「去支付」或「查询支付结果」。只有有权创建支付的状态才显示创建按钮。 |
| `FAILED` 或本人当前单确认 `NOT_FOUND` | `canStartNew=true` 且 `nextAction=RETRY_ORDER` 时可重新选票。 `canStartNew=true` 且 `nextAction=START_ORDER` 时可开始选票。 |
| `A0307`、重复购买 | 停止原号异参提交，通过原单续查入口定位。业务结果明确后再依据实际允许动作处理。 |
| `PAID`、`TICKETED`、`CLOSED`、`REFUNDING`、`REFUNDED` | 跟随详情、出票或退款状态。订单关闭后的异常到账显示在同一订单的退款进度内。 |

进入确认页先查询一次原请求，服务端要求等待时到时间再发。累计 30 秒后提示「仍在确认，可去我的订单继续查看」，基础查询间隔改为 15 秒。累计两分钟提供「手动刷新」并停止周期查询。按首次确认记录的时间起算，能找到记录的刷新和回到页面不重置阶段。切后台取消下次定时查询，回前台在允许的时间查一次，手动阶段不重开周期查询。

每次查询结束后再排下一次。起步间隔为 1、2、4、5 秒，后续 5 秒。取本地间隔、`retryAfterMs` 和适用的 `Retry-After` 中的较长值，再随机增加 0–249 ms。兼容响应缺少 `retryAfterMs` 时可读 `pollIntervalMs`。已确认的原单状态不会被晚到的在途响应覆盖。重新登录后原账号可恢复。离开路由后只保留续查线索。

[原单恢复 #12](../issues/ISSUE-012-seckill-request-recovery.md) · [订单确认 #13](../issues/ISSUE-013-order-confirmation-experience.md)

### 5.3 支付与倒计时

- 等待创单或查不到事实时，页面展示确认中。订单状态进入 `WAIT_PAY` 后，用订单响应的 `paymentCreateDeadline` 显示创建支付的剩余时间。已有支付单时用该支付单的 `paymentExpireTime`。订单关单时点单独来自 `expireTime`。
- 使用对应订单或已有支付单响应里的带时区 `serverTime` 校准剩余时长，在当前页面用 `performance.now()` 推进。切回前台、支付回跳和本地计时到零时触发原单查询。时间字段缺失或解析失败时先提供「查询支付结果」。服务端的订单与支付状态决定下一步。
- 创建支付的保护窗从 `paymentCreateDeadline` 起，到订单原关单时点 `expireTime`。现行服务端默认提前 30 秒停止建支付单，页面直接读截止字段。到达保护窗后使用 `GET /api/v1/payments/order/{orderNo}` 或已有 `payNo` 的 `GET /api/v1/payments/{payNo}`，并查询原订单状态。支付意图创建结果未知时走同一路径。浏览器关闭、跳转参数和本地倒计时都只是继续查询的触发器。
- 主动取消时展示影响并要求确认。等待结果时显示「正在确认取消」。渠道结果待确认时保留「查询支付结果」。已付款时展示原订单和出票入口。订单关闭后晚到账，显示原单的异常退款进度。

| 资金或票据接口结果 | 文案和动作 |
| --- | --- |
| 支付 `INIT` 且 `nextAction=PAY`，订单仍可付款且未达实际支付截止 | 显示金额和截止，继续同一个支付单。保护窗内没有新建或继续支付操作，可查询原单。 |
| 支付返回 `CHECK_PAYMENT`，或创建支付的响应丢失 | 「支付结果待确认」，查原单关联的支付记录与订单。 |
| 支付 `SUCCESS` 且 `nextAction=VIEW_ORDER`，出票接口尚未给出可展示票 | 「已付款，正在出票」，查看原订单并更新出票状态。 |
| 出票接口返回已签发票据 | 「查看电子票」，显示票号、座位和入场规则。 |
| 支付 `ABNORMAL_PAID` | 「已关闭订单的付款正在处理退款」，查看同一异常退款单。 |
| 退款 `PROCESSING` / `SUCCESS` / `FAILED` | 分别显示处理中、已完成、需联系支持。处理中且 `payRefundStatus=SUCCESS` 时写「已确认退款，订单仍在更新」。 `MANUAL_CHECK` 显示「退款结果待核对」。 |

### 6.2 键盘与读屏

- 以 WCAG 2.2 AA 为目标。正文通常至少 4.5:1，对比度要求适用的大字与非文本控件边界至少 3:1。普通触控操作以 44×44 CSS px 为项目目标。图形上的密集座位提供等价列表及可放大的入口。核验对比度、拖动替代、最小命中区和焦点遮挡。
- 页面提供跳到主内容链接和连续可见焦点。固定底栏须在 320 px、200% 文本缩放、竖屏软键盘状态下避开当前焦点。桌面主内容 `Tab` 顺序与阅读顺序一致。路由切换优先聚焦新页面主标题，字段或选座错误聚焦到能恢复操作的位置。

- 状态变化通过 `role="status"` 或合适的 live region 报告。表单错误需要可定位到具体字段。确认中、可支付、过期和支付确认结果仅在实际状态改变时播报，不逐秒播报倒计时。选座标签包含分区、排、号、价位和状态，图例文字能独立解释颜色。

### 7.3 数据与故障处理

- HTTP 状态和业务 `code` 分别读。HTTP 200 允许携带领域拒绝，202 有待确认语义，401 走重新登录，429 按 `Retry-After` 等待，503 根据业务码恢复原请求或等待依赖恢复。未知业务码用通用可恢复界面与追踪号。网络中断后的写结果默认待查，按号或本人当前单找回。
- 64 位 ID、版本字段和金额按服务端实际类型处理。对契约约定为十进制字符串的字段保留原样，版本比较用精确整数或等价的十进制比较。金额用整数分做显示和必要的本地估算，展示服务端确认价。座位索引与张数遵从 DTO 数值边界。时间值带时区，售卖门禁由服务端决定。
- 会话凭证默认内存保存。若持续登录是产品需求，需在部署前拍板同源会话方案和回跳处理。跨页续查记录只保存账号隔离的场次、请求号、可选订单号及记录时间。凭证失效时隐藏原账号状态并暂停轮询，同账号重新登录后可恢复记录。主动退出或换账号时清理前一账号的本机记录，原单仍可从后端按当前账号查询。续查服务必须验证归属。
- 支付回跳重新查询原单。真实支付只接受 #23 确认的发起方式和站点。接口说明和用户输入以文本渲染。海报使用站内路径或已配置的授权资源站点。帮助链接只跳转到预先配置的站内路由或站点。Mock 扣款与故障开关仅在隔离演示环境可见。真实金额、身份信息、验票码、查询凭证与原始响应从埋点、测试截图和错误日志中排除。
- 共用请求层支持 `AbortController`，场次、分区和账号切换采用请求代次检查。重放写操作只有业务层在确认相同请求、参数、凭证和允许条件后发起。对用户展示的订单号以本人服务端结果为准。
