# ISSUE-015 独立候场与跨设备恢复排队顺序

[开发与云端验收设计](../domains/05-waiting-room.md)

## 业务与范围

开售前可进入候场，刷新或换设备保持位置，未轮到时显示已知等待区间或「仍在排队」。复用 `JwtAuthGlobalFilter` 和已有 `UserFacade` 实名结果。A 首发依赖现有一证一账号唯一约束，018 与 021 接入后的场次使用场次级证件标识。正式放行由 016 接手，本单用测试驱动读取候场顺序。

## 接口与参数

| 入口 | 入参与权限 | 正常和异常行为 |
| --- | --- | --- |
| `POST /api/v1/shows/{showId}/queue` | JWT，正数 `showId`，可带已显示的正整数 `saleConfigVersion`；当前版本由服务端取得。 | 幂等加入或恢复当前记录。`200` 返回状态和只读 `queueReadToken`。版本变化返回新版本与下一步，未实名引导核验，限频返回 `429` 与建议等待。 |
| `GET /api/v1/shows/{showId}/queue/me` | 本人登录态或仅限本场、本队列记录的只读凭证。 | `queueStatus, retryAfterMs, serverTime, waitEstimate?`。本单实现 `WAITING/EXPIRED/ENDED`，由后续 Issue 补放行、验证和售罄。个人响应 `Cache-Control: no-store`。 |

只读候场凭证用独立用途、短期签名和记录期限，不授予交易权限。初始刷新建议 20～30 秒带抖动，热态读取无须同步访问订单、库存或实名 DB。换设备需登录一次再续用本人记录。

## 数据与实现顺序

1. 在边缘候场适配器背后用独立存储记录 `(showId,saleConfigVersion,queueId,userId,identityKey,phase,rank,expiresAt)`。两类唯一约束为场次版本内活动账号和同场活动证件。队列分区只与候场有关，需求峰值按 027 实测。有效状态以 TTL 或过期索引清理。
2. 服务端决定入队时间。开售前一个批次，封闭后以同一开售版本、同一随机结果生成固定顺序。开售后取原子递增顺序，排在预排批次之后。多实例采用单个批次封闭裁决，时间相等按服务端顺序号。旧代记录禁止复用到改期新代，给用户新入口。
3. `web-console/waiting-room.html` 展示开售时间、排序规则和低频刷新。切设备、刷新、凭证过期后重入只恢复原记录；候场依赖不可用给等待页和重试提示，服务端不创建绕行入口。

## 关闭条件

- [x] L1 在 `T0` 边界前后各 1 毫秒入队，开售前同批次，开售后按服务端顺序。重复加入、换设备、跨账号凭证和改期均可验。
- [x] L2 多实例并发一账号重复入队与队列封闭，活动记录唯一、预排序不重复生成、后入不越过预排批次。
- [x] L3 用依赖调用计数证明候场状态洪峰不读订单库、实时库存槽或短信接口。候场存储失败恢复后保留已有顺序，页面能恢复。
