# StarShow Issue 编写与验收规范

里程碑、缺陷和功能使用 `ISSUE-NNN-主题.md` 记录。历史链路一从 [ISSUE-001](ISSUE-001-chain1-user-reservation.md) 进入。

## 编写规则

1. 文件开头写 `issue_id`、`title`、`type`、`priority`、`milestone`、`status`、`parent_issue` 和 `blocked_by`。`P0` 表示正式开售硬门禁或资金、库存风险，`P1` 表示上线前应完成的体验或运营交付。`blocked_by` 只列直接阻塞。有评审或商户、场馆等外部前置条件时，在正文写出负责人及通过证据。
2. **业务与范围**说明谁在什么场景下使用、做完后能看到什么，引用现状入口。每张实现单交付可用接口、可演示流程或可独立复验的结果。把同模块但可独立交付的功能拆开。
3. **接口与参数**写 Method、Path、鉴权、入参类型与校验、服务端推导字段、正常结果、异常语义和重试方式。涉及唯一键、状态或配置的 Issue 说明版本、时钟、有效期和边界值。给新结果码标明是否拟定，实施时同步 [API 契约](../contracts/API_CONTRACT.md)。
4. **数据与实现顺序**写事实源、存储结构、关键索引、事务边界、Redis 占用归属、消息兼容、失败恢复和滚动升级。优先给仓库里的 Controller、Service、Lua、SQL 或脚本入口。新增迁移沿用 `docker/mysql/migrations/`，同时核对新库初始化和存量升级。
5. **关闭条件**采用可勾选断言，覆盖正向、越权或边界、故障与兼容路径。写清夹具、命令入口、观测值和附件。状态从 `Draft` 经规格评审和直接依赖交付进入 `Ready`，实际验收通过并有证据后才记 `Done`。

## 实施与评审清单

| 检查项 | 提交成果 |
| --- | --- |
| 业务演示 | 提供能复现的请求或页面操作。从一条正常路径开始，再演示最重要的失败恢复。 |
| 接口变更 | 对齐 [API 契约](../contracts/API_CONTRACT.md) 和链路文档。ID 及金额按契约使用十进制字符串，金额在库内用 `BIGINT` 存分，时间带时区，用户身份从可信上下文取得。 |
| 兼容与隔离 | 检查旧客户端、存量记录、旧消息和非试点场次。聚合态用本地 `*Facade` Bean，分布式用内部代理。 |
| 验证 | 在云服务器先跑 `mvn -B -pl <模块> -am test`，再按 Issue 跑真实中间件。L2/L3/L4 证据包括断言、日志摘要和实际环境。[总测试说明](../TESTING.md) |
| 内存与清理 | 测试串行执行，一次仅启动本用例的组件。先保存证据，再在 `finally` 按资源归属依次关闭本轮进程和中间件，检查端口和内存。继续下一轮前确认已退出。容量压测保留原负载和断言，使用分布式发生器时单独核对实际送达量。 |
| 证据与文档 | 在原 Issue 追加 [Prove-It 回执](../../.agents/skills/prove-it/SKILL.md)，同步关联链路、契约和 [进度账本](../PROGRESS.md)。只提交脱敏证据，不写证件、个人凭证、商户密钥或本机路径。 |

本地文档使用仓库现有 Issue 编号。若后续发布至 GitHub，为每张任务保留本地编号和依赖回链，避免把 GitHub 自动编号当成仓库编号。
