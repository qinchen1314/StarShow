# V1 → V4 抢票引擎真实压测实验报告（Phase 5 填充模板）

> 原则：严禁编造天文数字 QPS。所有数据必须在同一本机硬件、同一 5,000+ 独立 JWT Token 池、同一 10,000 张票池下实测得出，并附带自动一致断言结果。

## 1. 实验环境与控制变量

- **机器配置**：`待 Phase 5 实测填写（CPU 核数 / 内存 / OS）`
- **JVM 参数**：`待填写（-Xms / -Xmx / GC）`
- **中间件配置**：MySQL 8.0（连接池大小 / Buffer Pool）、Redis 7.4、RocketMQ 5.3.0
- **压测数据集**：演出 `showId=10001`，分为两组独立对照场景：
  - **售罄正确性组**：确保独立用户池人数 `>=` 总库存（如 5,000+ 独立已实名用户池对应 2,000~5,000 张票，或扩容至 10,000+ 用户池对应 10,000 张票），防止因一人限购一张导致用户池不足而无法验证售罄边界；
  - **高并发吞吐与积压组**：统一节奏与固定初始库存下对比 V1~V4 吞吐与 V4 排空耗时。
- **压测工具**：k6 / JMeter（脚本位于 `load-test/`）

## 4. 压测后强制正确性断言（`prove-it` L4）

每次压测结束自动执行核对：
1. 各轮先记录实际初始库存和选定策略。V1～V3 以 MySQL 库存路径对照，V4 排空后才核对 `Redis 已扣库存数 == MySQL t_order_0..3 有效订单总张数 <= 本轮初始库存`。
2. 所有策略核对 `t_ticket_tier.available_stock == 本轮初始可售库存 - MySQL 有效订单总张数`，按 `SUM(qty)` 统计，覆盖非一张订单场景。
3. `SELECT MAX(cnt) FROM (SELECT user_id, show_id, COUNT(*) cnt FROM t_order_* WHERE active_flag = 1 GROUP BY user_id, show_id) t <= 1`
4. V4 的 `starshow:deduct_pending:{showId}` ZSET 排空后长度为 `0`。单纯的 API 受理结果不代替落单计数。[链路三验收规格](../domains/03-order-seckill.md#七prove-it-设计验收与实施顺序)
