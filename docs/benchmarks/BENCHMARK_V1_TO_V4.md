# V1～V4 抢票压测报告（2026-11-22）

## 实验条件

- Windows 11，Intel Core i7-13620H，16 逻辑处理器、15.6 GiB 内存。同机 Docker 运行 MySQL 8.0.39（512 MiB buffer pool）、Redis 7.4 和 RocketMQ 5.3.0。测试 JVM 为 JDK 21.0.10，`-Xms32m -Xmx288m -Xss512k -XX:+UseSerialGC -XX:ActiveProcessorCount=4`。Hikari 上限 20、Tomcat 上限 72。独立 Redis 容器限额 160 MiB。
- 同一份 5,001 个独立 JWT 对应 5,001 条已实名合成数据。每轮对五个票档按用户编号轮询分配、每用户抢一张。64 个客户端工作线程串行跑八轮，每轮换新场次，开售前真实预热，并经 HTTP 预发同场次的短时下单凭证（压测 TTL 600 秒）。实名资料预置，JWT 由项目签发器签发，实际请求走聚合态鉴权、Spring MVC、MySQL、Redis 与 RocketMQ。每轮预热、领凭证、回放验收均在计时窗外。
- 两组分别为 2,000 张售罄压力和 10,000 张留余吞吐。两组每策略均提交 5,001 次，合计 40,008 次计时请求，另有 200 次赢家请求重放。前者验证卖光时的拒绝和库存守恒，后者检验还有余票时服务承受的并发。
- 并发入口直连聚合包的 HTTP 端口。用例没有计入网关、异地网络、预约、详情读、Pay/出票或测试报告外的多实例组件。四策略顺序固定为 V1～V4，各测一轮，数据用于定位瓶颈和验证正确性。

## 实测结果

## 售卖链路解读

- 万张组下，V4 让买家更早收到 202，但最后一笔落库耗时 105.310 秒。固定 30 次轮询、最大 3 秒间隔可能耗尽于订单落库前。页面应保留原请求和订单号，显示「仍在确认」，允许从订单页或换设备继续查。支付倒计时以持久化后的 `expireTime` 为准。
- 万张组 V4 的 InnoDB 行锁等待只有 1 次，仍出现约 99 秒在途积压。建议先分开记录创建消费、提交、Redis 状态更新和关单消息投递耗时。用已有 `CLOSE_CHECK` 待办把投递从创单消费线程移出的收益需要在同一基线下复测。多实例、同一热门票档倾斜和消费者故障也要纳入验证。
- 本次仅测下单路径。真实场次还要同轴观察开售前提醒迟到率、详情 P99、预约计数回源、网关限流以及开售后查单。增加实测前不可把表中 TPS 当成公网容量承诺。[万人演唱会复核](../reviews/chain-optimization-review.md#八以万人体育馆演唱会验收产品2026-11-22)

## 复跑

使用专用 MySQL 与空闲的非 0 Redis DB，执行：

```powershell
./scripts/verify-live-tests.ps1 -Chain Chain5
```

用例输出 `BENCH_ENV` 与 `BENCH_RESULT`，日志位于 `starshow-boot-all/target/Chain5LiveMiddlewareVerificationTest.log`。对照测量结束后脚本回收测试 schema 和 Redis 数据，再启动其他验收。整体用例耗时 426.9 秒，含准备、领凭证和核对。
